▚ AI 驱动体素资产 · 方案评估与推荐架构

「方块雄鹰」现有体素管线是确定性 Python 生成器（voxlib.py + gen_units.py / gen_pirate.py / gen_scene.py）。 本文评估：能否用大模型 + 提示词驱动体素资产生产，以及是否存在比「让模型直接生成体素」 更方便的方式。结论：有——把大模型放在「描述意图」层，让它产出声明式 spec， 由确定性编译器负责落地；本仓库完成该闭环所需的基建已具备约八成。

一句话结论：让大模型直接吐体素坐标，是所有方案里最不方便的一种。 真正的杠杆点是降低模型的输出规模——从「几千个体素坐标」降到「十几个部件描述」， 把正确性交给编译器，把判断力交给预览图。

1. AI 介入的四个层级

层级做法模型输出规模主要失败模式结论
L0 直接吐体素 模型直接写 {(x,y,z):color} 字典或 .vox 字节 O(体素数)，动辄上万 token 空间想象力弱 → 不对称 / 穿模 / 漂浮块；超 255 色；每次结果不可复现 反模式
L1 写生成器代码 提示词 → 模型写 build_e7() → 跑 gen_units.py O(行数)，数百 token 坐标仍靠猜；但可 review、可重跑、可 diff，靠预览图闭环 现状，性价比高
L2 产声明式 spec 提示词 → 模型写 JSON 部件描述 → 编译器展开为体素表 O(部件数)，数十 token 表达力受 op 集合限制（可逐步扩展） 推荐主攻
L3 生成式 3D 文生 / 图生 3D → 体素化 → 调色板量化 —（模态转换） 失去轴对齐方块风格；无对称 / 朝向 / 尺度保证；体素数易爆 仅适合不规则地貌

L0 与 L2 的差别全在输出规模。模型不是不会建模，而是不该被要求去当坐标计算器： 要求它逐格写出 3000 个体素，等于把「造型判断」和「整数运算」两件事捆在一起交给一个 不擅长算术的部件。这一层的 token 成本与出错率都随体素数线性上涨，而 L2 的输出随 部件数变化——一个 3000 体素的 E6 炮舰，用 spec 描述大约只需要 15~20 个 op。

当前的 L1 已经在用，只是人肉驱动。 gen_units.py 里每个 build_eX() 都是「一次提示词 → 一段代码」的产物。 L1 的隐含成本是每次改动都要人读代码确认有没有写错坐标，而 L2 把这段确认 转移给了编译器——这是 L2 相对 L1 的实际收益。

2. 为什么必须有编译器挡在中间

本工程的资产约束比一般项目硬，而这些约束放在编译器里是免费的，放在提示词里是碰运气：

约束出处 / 判据放在提示词里的后果
调色板 ≤ 255 色 voxlib.write_vox() 超出直接抛错 模型编出渐变配色 → 生成中断
单位量级带宽（见 §9.6 实测：宽 11~21 / 长 11~29 / 体素 175~2953） 正交 34 相机下过小则「认不出是什么」（旧版 E1~E5 只有 3~5 体素宽的教训） 造出 5 体素宽的装饰性敌机，游戏里不可辨
左右对称 _sym() / put() 的 2c-x 镜像 俯视下机体扭曲，「不像飞机」
轴对齐 + 无漂浮体素 asset_audit.gd：面中心内推 0.25 格须落在实心内 出现悬空方块，网格出现内面朝外的脏面
朝向（地面 -Y / 空中 +Y） look_at 让 -Z 指向目标，godot_z = vox_y 炮口朝后、机头背对玩家
SEED 可复现 地貌生成依赖固定种子 每次重跑结果不同，无法回归比对
架构原则：编译器应是唯一写 .vox 的出口。 大模型无论输出什么，都被这一层拦下——不合法就报错，不达标就回灌。 这让「模型胡编」的后果从「产出坏资产并进了游戏」降级为「一次失败的重试」。

3. 推荐架构

4. 声明式 spec 草案

spec 的 op 集合不需要从零设计——gen_units.py 里的建模原语 _sym / _symbox / _oct_skip 以及 build_player() 的 half[] 剖面表、build_e2() 的 hypot 环，本身就已经是一套 op 了。把它们从 Python 函数提升为 spec 的指令即可。

op 集合（对齐现有实现）

op对应现有代码参数
dotput(x,y,z,col)单点体素
symdot_sym(v,c,x,y,z,col)单点 + 自动镜像到 2c-x
box / symbox_symbox(...)x0..x1 / y0..y1 / z0..z1 区间填充
profilebuild_player() 的 half[]沿 y 的半宽表，生成流线机身/机翼
oct_oct_skip(dx,dy,r,cut)切角方形 → 八边形（炮塔/环体轮廓）

mirror_fill生成器统一约定声明镜像轴 c，整段对称

同一个 E7 用 L1（Python 代码）写约 60~80 行，用 L2 spec 约 15 行—— 模型的输出规模降低一个数量级，且对称性、调色板、包围盒由编译器保证，模型不必「记得」。

5. 编译器职责与校验项

编译器（建议 tools/vox/voxspec.py）只做三件事： 展开 op → 体素表、校验约束、落盘（直接复用 voxlib.write_vox，不改动它）。

校验项判据失败动作
调色板引用命名调色板，颜色数 ≤ 255报错，拒绝生成
包围盒量级宽 11~21、长 ≤29、体素 175~3000（§9.6 实测为准）警告 + 列出实际尺寸
左右对称逐 (y,z) 行做镜像比对报错（或按 axis 自动补对称）
连通性flood fill，主连通分量应覆盖 ≥99% 体素警告 + 输出漂浮块坐标
朝向facing 与 category 默认值一致报错
可复现随机类 op 强制显式 seed（编译器本身确定，见 §9.6）报错（用于回归闸门与漂移检测）
零回归闸门（阶段 0 的验收标准）：把现有 build_e1_base() → build_e4() → build_player() 按 §9.1 三级反向导出为 spec，重跑后 与现有 assets/vox/units/*.vox 逐体素比对必须完全一致。 达不到就说明 op 集合漏了原语，补齐即可——这保证「引入 spec」不引入任何视觉回归。

6. 本仓库已具备的基建

上图闭环里除了「spec 编译器」，其余环节仓库里都已存在且 headless 可跑， 这正是落地成本低的原因：

环节现有资产在闭环中的角色

附：被忽略的现成通道 —— addons/godot_ai

工程已在 project.godot 的 [editor_plugins] 中启用 res://addons/godot_ai/plugin.cfg，并有 autoload _mcp_game_helper。这是 Godot 内部的 MCP 桥，意味着大模型可以直接操纵 编辑器里的场景与资源，而不只是生成文件。若接通，「生成 → 在编辑器里看 → 改」 可以不出对话完成。它与本文的 spec 方案不冲突：spec 定义「产出什么」， MCP 桥定义「在哪儿看和改」。

8. 诚实的边界与风险

LLM 的空间想象力是天花板。 L2 能大幅降低 token 与畸形输出，但「这个造型在正交 34 相机下认不认得出」这类判断， 目前仍必须靠图。因此预览图人审这一步不能省——它是方案的安全阀，不是可选项。
  • 迁移现有资产不划算。player / boss / E1~E6 已调好，为统一格式而反推 spec 是纯成本。阶段 0 只反推 1~2 个资产作为编译器验证样本，其余按需迁移。
  • op 集合表达力有限。spec 天然不如 Python 自由。须保留可扩展性： 遇到表达不了的造型，应补一个 op，而不是往 spec 里塞代码（会重新引入 L1 的问题）。
  • 生成式 3D（L3）与现有美术风格冲突。本作是轴对齐体素风，光滑 mesh 体素化后 观感不同；且无对称 / 朝向 / 尺度保证，AABB 贴地对齐逻辑需重算。建议只用于不规则地貌 （岛 / 礁 / 沉船），不用于单位。
  • 真正划算的场景是「批量造新内容」：后续关卡敌机、更多海盗地图切片。 单件精修仍以 MagicaVoxel 手工微调最高效。

9. 评审修订（v2 · 2026-09-11 开工前走查）

开工前对照 gen_units.py 实码走查了一遍本方案， 确认基建描述属实，但发现六处需要修订的缺口与本三处数字不一致。本节为修订记录， 正文相关处已同步指向本节。

9.1 零回归闸门样本重排：E1 → E4 → player

原定首批反导 build_player() / build_e4()，但 build_player() （gen_units.py:86-131）是全文件条件涂色最重的函数—— wing = dx > 1 and 7 <= y <= 14、tip = dx >= h - 1、 stripe = dx == 1 and 5 <= y <= 15 这类「相对条件涂色」当前 op 集合表达不了。 拿它当首样本会触发本文警告过的路径：为过闸门往 op 里塞条件参数，spec 退化成编程语言。 改为三级推进，每级都过逐体素闸门：

级样本验证目标
1build_e1_base()基础 op：八边形柱 oct、symbox、dots 点枚举（无条件涂色）
2build_e4()profile 剖面 + edge 附着色（翼尖红）；翼面刻线用 dots 兜底（见 9.2）
3build_player()逐行层色（翼段与前後段层集合不同）+ 座舱/喷口 paint 覆盖

比对方式：按 (x,y,z) → (r,g,b) 比对， 不比调色板索引——write_vox() 按颜色排序生成索引， 而标准工作流允许 MagicaVoxel 手工精修（会重排调色板），比索引会误报。

9.2 op 集合补强：solid / paint 语义分离等四项

  • solid / paint 语义分离（新增核心设计）。 塑形类 op（box / symbox / oct / profile / dots）只负责添加体素； paint op 只对已存在体素改色，不新增。 这解决了「覆盖涂色时不小心长出新块」的问题（build_player 的白机鼻只应涂到已存在的格子上）， 也让 spec 更贴近建模心智：先塑形、再上色。不对称的 paint 不破坏镜像校验。
  • profile 逐行层色 + edge 附着。 build_player 同一剖面的每层 z 颜色不同（z0 腹暗 / z1 枪灰 / z2 侧条 / z3 顶面四色）， 且翼段与前後段层集合不同（翼段只有 z1/z2）—— profile op 需支持 per-z 色表，层集合差异靠「拆成多个 profile op 分段」表达，不引入通用条件式。 edge 附着规则（「距行外缘 n 格换色」）表达翼尖红这类相对条件， 不让模型做算术。
  • dots 点枚举兜底。 E4 的翼面刻线 (abs(dx)*2+y)%5==0 是数学条件，op 永不该表达它—— 这类零星装饰用 dots 显式枚举（十几个点），仍走镜像/调色板校验。主体结构用高级 op、 零星装饰用点枚举，输出规模原则不被破坏。
  • 多部件与多调色板。 E3 是「机身 + 独立旋翼层」两个 .vox，spec 顶层一开始就设计成 parts: [...]， 别等撞上再改 schema。命名色库分 player / enemy 两套（从 gen_units.py 原样搬运），新配色走「先入库、后引用」，不开放自由造色。

9.3 认物闭环补一环：视觉模型初筛

原方案认物完全靠人审。多模态模型恰恰擅长「这张俯视图像不像战斗机」—— 把 ingame_view.gd 的输出喂给视觉模型做第一轮筛选 （像 / 不像 / 缺什么特征），人只终审。不新增基建（预览图本来就在产），能砍掉大半人审轮次。 回灌格式需结构化：audit 报告从人读表格转 JSON，问题定位到 op 级（哪个 op 产生了漂浮块）， 并定义迭代上限（如 3 次失败转人工）。

9.4 与 MagicaVoxel 手工精修的真源策略

标准工作流允许「生成 → MagicaVoxel 精修 → 保存」，精修后 .vox 与 spec 即脱钩， spec 重跑会覆盖手工修改。对策：手工精修过的资产以 .vox 为真源， 对应 spec 标记废弃或删除；且 voxspec verify 兼作漂移检测器—— spec 与 .vox 不一致时报告差异，区分「编译器回归」（必须修）与「手工精修漂移」（更新或废弃 spec）。 两者都能被同一命令发现，这是把零回归闸门工具常态化的额外收益。

9.5 范围界定：spec v1 只覆盖「单位」

gen_pirate 的海面/岛屿是 64×64 噪声地形 + 随机撒点，与单位的「对称手工造型」是两种范式， 硬统一会撑爆 op 集合（需要 noise / scatter / 分带等着色 op）。地貌继续走 L1 Python 生成器； 若确需 AI 产地貌，另立 terrain spec，不与单位共用 schema。

9.6 数字修正与流程注记

  • bbox 阈值统一为实测值（2026-09-11 统计 assets/vox/units/）： 宽 11~21、长 11~29、体素 52~2953（旋翼层 52 除外，主体 175~2953）。原文档三处说法 （11~29 / 15~29 / 11~25）均与实测不符，已统一。
  • 「可复现」判据改为「随机类 op 强制显式 seed」—— 编译器确定性天然成立，要禁的是无 seed 随机 op。
  • GPU 环节进不了自动化：asset_review / ingame_view 需要开窗渲染（headless 出不了图），CI 只能挂 headless 审计；「一条命令」需区分 headless 部分与人触发的视觉部分。
  • spec 文件管理：specs 进 git （tools/vox/specs/*.json），文件名与产物 .vox 同名映射，改 spec = 改资产，diff 可读。

9.7 开工触发条件（决策记录）

L2 的收益取决于新单位需求量；若 E7 及后续只有十几个，L1 + 视觉模型初筛可能已够。 本方案于 2026-09-11 决策开工阶段 0~1（纯重构、零模型依赖、风险最低且立刻可用）， 阶段 2（模型产 spec）的启动以「确认下一批关卡需要 ≥10 个新单位」为触发条件，避免为方案而方案。
