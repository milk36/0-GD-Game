▚ 体素改瓦片 · 方案评估与建议

本文评估「把现有体素资产改为 tile 瓦片方式」这一方向，给出分层建议、必须先定死的规格， 以及与本仓库既有管线（voxspec.py spec 管线、gen_pirate.py 地形切片）的衔接方式。

一句话结论：瓦片应该只用在地貌与关卡摆件，且应走 「3D 模块化瓦片 + 网格排布 + GridMap 渲染」；不要退到 2D TileMapLayer， 也不要把单位瓦片化。瓦片化省的是「重复摆放与绘制」，不省「单块美术工作量」—— 真正的双赢组合是用 spec 管线产瓦片本体 + 用数据表排布。
▶ 配套演示：tile-3d-vs-2d-demo.html ——两侧跑同一份瓦片布局与同一套颜色，3D 侧用游戏真实相机（正交 34 / (0,30,12) / 方向光 (-52°,-28°)）软件投影， 可切 68°/90° 机位与地形高度，直观对比「瓦片+3D」与「纯 2D 瓦片」的观感差异。

3. 为什么不退到 2D TileMapLayer

那不是「省事」，是换引擎。以下能力会全部作废：

换言之：2D 化的代价约等于重写 game.gd 的 3D 部分（1700 行中的大半）， 而收益只有「地形自动拼接」一项——那不划算。

4. 推荐架构：三层分工

5. 关键洞察：本作的世界是一条「滚动走廊」，天然适合行式瓦片

当前世界沿 -Z 无限滚动（对象滚出后 z -= 230 回绕，并把 x 重新随机）， 玩家固定在 z≈0。这本身就是「行式瓦片」的形态——只是现在每行内容是随机的。 把它显式化成「行 → 瓦片列表」的映射后，随机撒点自然消失。

这条改造同时解决三个现存问题：

  • 不可复现 → 布局来自数据表，同关卡同种子恒定；
  • 不可设计 → 想摆什么摆什么，不必与随机数较劲；
  • 对象数波动 → 行级池化，运行时对象数恒定。

6. 必须先定死的三个数

这三点定不下来，瓦片拼装一定会出缝或错半格。 且它们都触及全工程共用的代码，改动要极其小心。

6.1 瓦片边长

现状：体素单位是 0.3 世界单位 / 体素（ENEMY_SCALE；玩家机 15×19 体素 = 4.5×5.7 世界单位）。

方案边长列数（视野 60.44）评价
整数世界单位 2.0 2.0 = 6.67 体素 31 体素除不尽 → 跨瓦片体素不连续、拼接错半格
整数世界单位 4.0 4.0 = 13.33 体素 16 同上，仍是除不尽
体素整数倍 16 体素 4.8 13（覆盖 62.4） ★ 推荐：体素严格对齐，粒度较细
体素整数倍 32 体素 9.6 7（覆盖 67.2） ★ 备选：块大、对象少，但地形细节粗
改体素缩放为 0.25 2.0 = 8 体素 31 世界单位凑成整数，但牵动全部已有单位与手感调参（玩家速 24 / 正交 34 / 贴地偏移全部要重调）

建议取 16 体素 = 4.8 世界单位。关键理由：把「边长」表达成体素整数倍， 体素网格才能跨瓦片连续（沙滩、浪纹这些要跨界延续的细节才不会断）。 不要为了凑整数世界单位去改 0.3 缩放——那是牵一发动全身的改动。

6.2 锚点

现状：voxel_model.gd::build_blocks() 以 AABB 中心为原点， 且键与几何中心差半格（README §6 记载的已知坑）。当前靠 -mesh.get_aabb().position.y * s - 0.1 反推贴海。

不要改 voxel_model.gd 的居中逻辑——单位资产、幸存者、 地形全部共用它，改了会让所有既有资产偏移半格。 对策：在瓦片侧另做锚点修正（或给 build_blocks 加一个可选参数、默认行为不变）。 建议瓦片统一采用底面中心锚点（x/z 居中、y 取底面）——走廊左右对称， 且布局是以 0 为轴的，中心锚最自然。

6.3 全局北向与旋转约定

godot(x,y,z) = vox(x,z,y)（Z-up → Y-up）。瓦片的「北」若不统一， rot 旋转拼图时会出现镜像错乱。

  • 规定瓦片的 +Y（vox 坐标）即游戏 -Z（远端 / 前进方向）；
  • rot 只允许 0 / 90 / 180 / 270 四个值，不承担镜像；
  • 需要镜像的瓦片另设 flip 标志并显式声明（体素模型镜像后法线绕序会反转， 必须同时翻转绕序，否则 asset_audit.gd 的「绕序 100% 朝外」会失守）。

7. 渲染层选型

方案适用优点代价
GridMap + MeshLibrary 地面 / 礁石 / 建筑等格状地貌 Godot 原生格网摆放；mesh 与材质共享；同 mesh 格子实例化提交 单元格是立方体，高低差靠多层 cell 表达，需提前规划层数
MultiMeshInstance3D 同一造型的大量重复（波浪、浪花、碎石） 1 次绘制承担 N 个实例；项目已在子弹 / 星星 / 碎片上用此法 每实例只能调变换与颜色，不能各自换材质
合并 mesh（VoxelModel.build_blocks） 整行 / 整段的静态地貌 最简单；现有 island_scene.vox 已用此法 合并后无法单独移动其中一块，行滚动时需整行重建

建议组合：重复小件走 MultiMesh（波浪），格状地貌走 GridMap，一次性的整块地形走合并 mesh。 当前 VoxelModel.shaded_material() 在 _make_island / _make_reef / _make_wreck / _spawn_vox_decor 里每个摆件都 new 一份—— 瓦片化后改为 MeshLibrary 共享资源，可顺带修掉材质重复。

9. 与既有 spec 管线的关系

复用不复用（须另立）
  • voxspec.py 的 _op_* 实现（box/symbox/oct/ring/profile/dots/paint）可直接 import
  • voxlib.write_vox 落盘出口（一行不改）
  • 连通性 / 调色板校验思路
  • gen_spec.py 的批量 + 预览流程
  • category 现只允许 air|ground，且强制左右对称—— 地形瓦片天然不对称（海边、崖壁）
  • BAND 量级带（宽 11~21 / 长 ≤29 / 体素 175~3000）是单位实测值，对瓦片不适用
  • 敌机 facing 必须 +Y 的规则不适用于瓦片
建议：按 §9.5 的精神另立 terrain schema（voxspec 中增加 category: "terrain" 分支，或新建 terrainspec.py 而 from voxspec import _op_*）， 共用 op 实现、不共用校验与 schema。这样既不撑爆单位 op 集合，又不重复实现展开逻辑。

11. 风险与边界

  • 瓦片化不省单块美术工作量。它省的是重复摆放与绘制。所以真正双赢的组合是 AI spec 产瓦片本体 + 数据表排布——前者把单块成本压到十几个 op，后者把摆放压到一行数据。
  • 单位不要瓦片化。player / boss / E1~E10 是唯一造型，正交 34 下已要求 11~21 体素宽， 瓦片化直接毁掉辨识度（specs/PROMPT.md 的「换 silhouette」纪律会失效）。
  • 别为做瓦片而扩张 op 集合。§9.2 记录过这个教训：为过闸门往 op 里塞条件参数， spec 会退化成编程语言。地形需要 noise / scatter / 分带时，那些属于 terrain schema，不该混进单位 op。
  • GridMap 的层数要提前规划。单元格是立方体，地貌高低差（海面 / 沙滩 / 台地 / 建筑） 需要多层 cell；若把不同高度的东西塞进同一层，会出现互相穿插。
  • 镜像瓦片要同步翻转绕序。体素模型镜像后三角面绕序反转，会被背面剔除， 表现为「一块瓦片凭空消失」或「看到内部底面」。
